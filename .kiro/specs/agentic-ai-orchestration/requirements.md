# Requirements Document

## Introduction

This feature transforms the Campus AI Canvas Platform from a keyword-based routing framework into a true agentic AI system. The current LangGraph orchestration uses hardcoded keyword lists (VISUAL_HINTS, QUIZ_HINTS, EDIT_HINTS) for routing decisions, with LLM fallback only for ambiguous cases. The new system introduces LLM-driven intelligent routing, tool-use capabilities, multi-step planning, conversation memory, self-correction loops, and a tiered model strategy for cost efficiency. The transformation must preserve full compatibility with the existing Next.js frontend and Vercel AI SDK streaming protocol.

## Glossary

- **Orchestrator**: The LangGraph-based agentic supervisor that uses LLM reasoning to route requests, plan multi-step tasks, and coordinate module agents
- **Agent_Node**: A LangGraph node that wraps an LLM call with a specific system prompt, tool bindings, and retry logic to perform a specialized task
- **Tool**: A callable function registered with an Agent_Node that the LLM can invoke during reasoning (e.g., search, calculate, retrieve documents)
- **Router_LLM**: A small, cost-efficient model (e.g., Qwen3-30B-A3B) used exclusively for intent classification and routing decisions
- **Worker_LLM**: A larger, more capable model used for complex generation tasks like diagram creation, quiz generation, and multi-step reasoning
- **Conversation_Memory**: A per-session store of message history and extracted context that persists across turns within a chat session
- **Tool_Registry**: A centralized registry where available tools are declared with their schemas so Agent_Nodes can discover and invoke them
- **Execution_Plan**: A structured sequence of sub-tasks generated by the Orchestrator when a user request requires multiple steps
- **Self_Correction_Loop**: A retry mechanism where an Agent_Node validates its own output and re-prompts with error context on failure
- **Tiered_Model_Strategy**: The practice of using cheaper models for simple tasks (routing, classification) and reserving expensive models for complex generation
- **Canvas_Envelope**: The stable top-level JSON wrapper (with canvas_type discriminator) that the frontend uses to render visual modules
- **SSE_Stream**: The Server-Sent Events protocol used to deliver incremental UIMessage parts to the Next.js frontend
- **Intent_Classification**: The process of determining what type of response a user request requires (conversation, diagram, quiz, or multi-step)
- **Nebius_API**: The OpenAI-compatible LLM provider used by the platform for all model inference

## Requirements

### Requirement 1: LLM-Driven Intent Classification

**User Story:** As a university student, I want the system to intelligently understand my intent from natural language, so that I get the correct response type without needing to use specific keywords.

#### Acceptance Criteria

1. WHEN a user message is received, THE Orchestrator SHALL classify the intent using the Router_LLM instead of keyword pattern matching
2. WHEN the Router_LLM classifies an intent, THE Orchestrator SHALL include a confidence score between 0.0 and 1.0 and a reasoning trace as a human-readable string explaining the classification rationale in the classification result
3. WHEN the Router_LLM confidence score falls below a configurable threshold (default 0.6, configurable via environment variable between 0.0 and 1.0), THE Orchestrator SHALL respond with a clarification message asking the user to specify their intent from the available categories before routing to any module
4. THE Orchestrator SHALL support at minimum the following intent categories: conversation, diagram, quiz, and multi_step
5. WHEN a new intent category is added, THE Orchestrator SHALL require only a schema extension and prompt update without code changes to the routing logic
6. WHILE the Router_LLM is processing, THE Orchestrator SHALL complete intent classification within 800 milliseconds for single-turn requests where no Conversation_Memory context retrieval is required
7. WHEN a user responds to a clarification request with a valid intent category selection, THE Orchestrator SHALL route directly to the selected category without re-running classification

### Requirement 2: Tiered Model Strategy for Cost Efficiency

**User Story:** As a project maintainer, I want the system to use cheaper models for simple tasks and expensive models only when needed, so that operational costs remain low for a student project.

#### Acceptance Criteria

1. THE Tiered_Model_Strategy SHALL define at least two model tiers: a Router_LLM tier for classification tasks and a Worker_LLM tier for generation tasks
2. WHEN a request is classified as intent classification or single-turn conversational response that produces no Canvas_Envelope output, THE Orchestrator SHALL use the Router_LLM exclusively
3. WHEN a request is classified as diagram generation, quiz generation, or multi_step intent, THE Orchestrator SHALL delegate to the Worker_LLM
4. THE Tiered_Model_Strategy SHALL allow model assignments to be configured via environment variables (one variable per tier) without code changes
5. IF the Worker_LLM fails to respond due to connection error, HTTP error status, or response timeout exceeding 10 seconds, THEN THE Orchestrator SHALL fall back to the Router_LLM and include a degraded-quality warning indicator in the SSE_Stream response metadata
6. THE Tiered_Model_Strategy SHALL log token usage per request including: the tier used, prompt token count, completion token count, and a timestamp
7. WHEN the Orchestrator selects a model tier for a request, THE Orchestrator SHALL record the tier selection decision in the response metadata so that cost attribution is traceable per intent category

### Requirement 3: Tool-Use Capability

**User Story:** As a university student, I want the AI to be able to call external tools (search, calculate, retrieve documents), so that it can provide accurate and enriched answers beyond its training data.

#### Acceptance Criteria

1. THE Tool_Registry SHALL provide a declarative interface for registering tools with name, description, and JSON schema for parameters
2. WHEN an Agent_Node determines that one or more tool calls are needed during a single reasoning turn, THE Agent_Node SHALL invoke each tool through the Tool_Registry and include the tool results as content within its response text
3. THE Tool_Registry SHALL support at minimum the following built-in tools: web_search, calculator, and document_retriever
4. WHEN a tool invocation fails due to a timeout exceeding 10 seconds, a runtime exception, or an invalid response that does not conform to the tool's output schema, THE Agent_Node SHALL retry once with the same parameters before falling back to a response without that tool's results
5. WHEN a tool invocation succeeds, THE Agent_Node SHALL include in its response metadata a citation containing the tool name, invocation timestamp, and a summary of the query parameters used
6. THE Tool_Registry SHALL enforce a maximum execution timeout of 10 seconds per tool invocation
7. THE Tool_Registry SHALL truncate any single tool result that exceeds 4000 characters before passing it to the Agent_Node, preserving the first 4000 characters

### Requirement 4: Multi-Step Planning

**User Story:** As a university student, I want the system to break complex requests into logical sub-tasks and execute them in sequence, so that I get comprehensive answers to multi-part questions.

#### Acceptance Criteria

1. WHEN the Orchestrator classifies a request as multi_step intent, THE Orchestrator SHALL generate an Execution_Plan containing ordered sub-tasks—each with a sequence number, description, and assigned Agent_Node—before executing any of them
2. THE Execution_Plan SHALL contain between 2 and 5 sub-tasks for any single user request
3. WHEN an Execution_Plan is generated, THE Orchestrator SHALL stream a plan summary listing the number of sub-tasks and a one-line description of each to the user before beginning execution
4. WHILE executing an Execution_Plan, THE Orchestrator SHALL stream a progress update as a text part through the SSE_Stream at the start of each sub-task indicating which sub-task (by sequence number and description) is now executing
5. IF a sub-task in the Execution_Plan fails due to an Agent_Node error, a timeout exceeding 30 seconds, or an output validation failure, THEN THE Orchestrator SHALL skip the failed sub-task, continue with remaining tasks, and include in the final response which sub-task failed and the reason for failure
6. WHEN all sub-tasks complete, THE Orchestrator SHALL synthesize results into a single response that references each sub-task's output in sequence order, with an optional Canvas_Envelope if any sub-task produced visual output
7. WHILE executing an Execution_Plan, IF a sub-task has not returned a result within 30 seconds, THEN THE Orchestrator SHALL treat that sub-task as failed due to timeout

### Requirement 5: Conversation Memory

**User Story:** As a university student, I want the AI to remember what we discussed earlier in the session, so that I can have natural follow-up conversations without repeating context.

#### Acceptance Criteria

1. THE Conversation_Memory SHALL persist all user and assistant messages for the duration of a chat session, up to the configured maximum message limit
2. WHEN a new user message arrives, THE Orchestrator SHALL include the most recent 8 messages (user and assistant) from Conversation_Memory plus any extracted session metadata in the LLM prompt
3. WHEN the total message count (user and assistant messages combined) exceeds 50, THE Conversation_Memory SHALL evict the oldest messages to maintain the limit while preserving session metadata
4. WHEN the Conversation_Memory contains a prior Canvas_Envelope, THE Orchestrator SHALL include the canvas_type and subject from that envelope as context in the Router_LLM classification prompt for follow-up messages
5. WHEN a user or assistant message is stored, THE Conversation_Memory SHALL extract and store entity references (topic names, diagram types, quiz subjects) as session metadata, retaining a maximum of 20 entities per session
6. IF the session has been inactive for more than 30 minutes, THEN THE Conversation_Memory SHALL delete all stored messages and session metadata for that session, requiring the user to begin a new conversation without prior context
7. WHEN the Conversation_Memory is empty and a new user message arrives, THE Orchestrator SHALL proceed with intent classification using only the current message without injecting prior context

### Requirement 6: Self-Correction Loop

**User Story:** As a university student, I want the system to automatically retry and fix malformed outputs, so that I always receive valid and useful responses.

#### Acceptance Criteria

1. WHEN an Agent_Node produces output that fails validation against its expected schema, THE Self_Correction_Loop SHALL re-prompt the LLM with the original request, the malformed output, and the specific validation error message
2. THE Self_Correction_Loop SHALL attempt a maximum of 2 retries, each with a timeout of 30 seconds, before falling back to a structured fallback response
3. WHEN all retry attempts are exhausted or timed out, THE Agent_Node SHALL return a fallback response that conforms to the Canvas_Envelope format for the originating module (e.g., a fallback diagram Canvas_Envelope for the diagram module, a fallback quiz Canvas_Envelope for the quiz module) so the frontend can render it without error
4. THE Self_Correction_Loop SHALL log each retry attempt with the validation error type and the attempt number for observability
5. WHILE the Self_Correction_Loop is retrying, THE SSE_Stream SHALL emit text-delta events containing a "thinking" status indicator at least once every 3 seconds until the retry resolves or all attempts are exhausted
6. WHEN the first retry attempt succeeds with valid output, THE Self_Correction_Loop SHALL immediately return the corrected output without attempting further retries

### Requirement 7: Streaming Compatibility

**User Story:** As a frontend developer, I want the agentic system to maintain full compatibility with the existing Vercel AI SDK streaming protocol, so that no frontend changes are required for basic chat functionality.

#### Acceptance Criteria

1. THE SSE_Stream SHALL continue to emit the existing message lifecycle events in the following fixed order: start, text-start, one or more text-delta, text-end, optionally data-canvas, and finish
2. WHEN the Orchestrator performs multi-step reasoning, THE SSE_Stream SHALL emit intermediate text-delta events within 2 seconds of each sub-task beginning execution so the user sees incremental progress
3. WHEN an Agent_Node invokes a tool, THE SSE_Stream SHALL emit an optional event of type "tool-call" containing the tool name and a status field with one of the values: "started", "completed", or "failed"
4. WHEN the Orchestrator begins a new sub-task in an Execution_Plan, THE SSE_Stream SHALL emit an optional event of type "plan-step" containing the sub-task description and its ordinal position within the plan
5. WHEN a Canvas_Envelope is produced by any Agent_Node, THE SSE_Stream SHALL emit it as a data-canvas event using the existing JSON structure with fields: type ("data-canvas"), id (string), and data (the Canvas_Envelope JSON object)
6. THE SSE_Stream SHALL terminate every response with "data: [DONE]\n\n" regardless of whether the response involved tools, planning, or simple conversation
7. IF the SSE_Stream connection is interrupted before the finish event is emitted, THEN THE SSE_Stream SHALL not emit "data: [DONE]\n\n" so the frontend can detect an incomplete response

### Requirement 8: Extensible Agent Architecture

**User Story:** As a developer, I want to add new module agents (flashcards, task boards) without modifying the core orchestration logic, so that the platform can grow incrementally.

#### Acceptance Criteria

1. THE Orchestrator SHALL discover available Agent_Nodes through a registration interface rather than hardcoded references
2. WHEN a new Agent_Node is registered, THE Orchestrator SHALL include it in intent classification starting from the next incoming user request, without requiring changes to the routing prompt template
3. THE Agent_Node registration interface SHALL require: a unique name (maximum 64 characters, alphanumeric and underscores only), a description for the Router_LLM (maximum 200 characters), a callable that accepts a GraphState and returns a GraphState, a list of bound tools (0 to 10 entries), and the target model tier
4. WHEN an Agent_Node is registered, THE LangGraph workflow SHALL add it as a new node with conditional edges from the Orchestrator without requiring reinitialization of existing nodes or their state
5. THE Orchestrator SHALL support a minimum of 8 concurrent Agent_Nodes while maintaining at least 90% routing accuracy as measured against a labeled intent test set
6. WHEN an Agent_Node is removed from the registry, THE Orchestrator SHALL exclude it from future routing decisions within the same process lifecycle
7. IF an Agent_Node registration is attempted with a name that already exists in the registry, THEN THE registration interface SHALL reject the registration and return an error indicating a duplicate name conflict
8. IF an Agent_Node registration is attempted with missing or invalid required fields, THEN THE registration interface SHALL reject the registration and return an error indicating which fields failed validation

### Requirement 9: Cross-Module Awareness

**User Story:** As a university student, I want the AI to understand context from one module when I switch to another, so that asking for a quiz about a diagram I just created works seamlessly.

#### Acceptance Criteria

1. WHEN a user references content from a previous module interaction (e.g., "quiz me on that diagram"), THE Orchestrator SHALL retrieve the most recent matching Canvas_Envelope from Conversation_Memory based on the module type identified by the Router_LLM
2. WHEN routing to a module Agent_Node, THE Orchestrator SHALL pass cross-module context consisting of the referenced Canvas_Envelope payload and its associated session metadata extracted from Conversation_Memory
3. THE Orchestrator SHALL detect implicit cross-module references using the Router_LLM rather than keyword matching
4. WHEN cross-module context is passed to an Agent_Node, THE Agent_Node SHALL include the referenced Canvas_Envelope content as a context section in its generation prompt, truncated to a maximum of 2000 tokens
5. IF the referenced cross-module content is no longer in Conversation_Memory, THEN THE Orchestrator SHALL respond with a message indicating that the referenced content is unavailable and suggest the user recreate or re-upload it
6. IF the Router_LLM identifies a cross-module reference but multiple matching Canvas_Envelopes exist in Conversation_Memory, THEN THE Orchestrator SHALL select the most recently created match and include its canvas_type in the context passed to the Agent_Node
7. WHEN the Orchestrator retrieves cross-module context successfully, THE Orchestrator SHALL include the source canvas_type and creation turn number in the routing metadata passed to the target Agent_Node

### Requirement 10: Error Resilience and Graceful Degradation

**User Story:** As a university student, I want the system to always give me a useful response even when parts of it fail, so that my study flow is never completely interrupted.

#### Acceptance Criteria

1. IF the Router_LLM fails to respond within 5 seconds or returns a connection error, THEN THE Orchestrator SHALL fall back to a keyword-based classifier that maps the user message to an intent category using the existing keyword lists
2. IF a Worker_LLM call times out after 30 seconds, THEN THE Orchestrator SHALL cancel the request and return a timeout explanation to the user through the SSE_Stream
3. WHEN any Agent_Node encounters an error that persists after the Self_Correction_Loop exhausts its maximum retries, THE Orchestrator SHALL return a conversational fallback response through the SSE_Stream explaining which module failed and suggesting the user rephrase or try again
4. THE Orchestrator SHALL implement circuit-breaker logic that disables a failing Agent_Node after 3 consecutive failures within a 5-minute window, keeping the circuit open for 60 seconds before transitioning to a half-open state that allows a single probe request
5. WHEN the circuit breaker activates for an Agent_Node, THE Orchestrator SHALL route affected requests to the conversation module with an explanation that the requested capability is temporarily degraded
6. IF all LLM providers are unavailable, THEN THE Orchestrator SHALL return a static maintenance message through the SSE_Stream and terminate the response with the standard "data: [DONE]\n\n" sequence
7. WHEN a circuit breaker transitions to half-open state and the probe request succeeds, THE Orchestrator SHALL close the circuit and resume normal routing to the recovered Agent_Node
